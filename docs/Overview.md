# Общая концепция

Telegram-бот для мониторинга и управления VPS-сервером. Развертывается в Docker-контейнере на целевом хосте с доступом к Docker API и файловой системе хоста.

**Docker-конфигурация:**
```yaml
bot:
  user: "0:0"
  volumes:
    - /:/mnt/host
    - /var/run/docker.sock:/var/run/docker.sock
```

---

# Безопасность и доступ

- Бот обслуживает **единственного пользователя** (владельца), идентификатор которого задается через переменную окружения `BOT_OWNER`
- Все команды принимаются и обрабатываются **исключительно от авторизованного пользователя**
- Дополнительная авторизация/whitelist на текущем этапе не требуется
- Бот имеет полный доступ к системным настройкам: крон-задачи, переменные окружения, скрипты, деплой

---

# Конфигурация

**Обязательные переменные окружения:**
- `BOT_TOKEN` — токен Telegram Bot API
- `BOT_OWNER` — Telegram user ID владельца (единственный авторизованный пользователь)
- `BACKUP_PATH` — абсолютный путь к директории с бэкапами БД (пример: `/home/ai_service/ai-stack/backups/postgres`)
- `TIMEZONE` — временная зона для форматирования дат (UTC на сервере, UTC+3 при отправке в бот)

**Настройки мониторинга:**
- Отслеживаются **все** Docker-контейнеры на хосте без фильтрации
- Таймауты и интервалы опроса: **1 минута** (универсальное значение для всех операций)
- Троттлинг уведомлений: **не чаще 1 раза в минуту** для каждого типа события

**Конфигурация загружается через pydantic-settings** с валидацией на старте приложения.

# Функционал

## 1. Команда `/start`

- Авторизует пользователя и открывает доступ к функциям бота
- Отправляет приветственное сообщение с IP-адресом сервера и текущим временем (UTC+3)
- Команды `/help` и `/cancel` **не реализуются** (логика обеспечивается retry-политикой и отказоустойчивостью)

---

## 2. Просмотр состояния сервера `/health`

**Снапшот метрик создается в момент запроса.**

### Метрики RAM:
- **Формат вывода:** `Занято: <abs> | <percent>%, Свободно: <abs> | <percent>%, Всего: <total>`
- Единицы измерения выбираются автоматически (MB/GB в зависимости от величины, 1 MB = 1024 KB, 1 GB = 1024 MB)

### Метрики CPU:
- Количество ядер (физических/логических)
- Load Average: **1 min / 5 min / 15 min** (классическая нагрузка Linux)
- Текущая утилизация в процентах (срез на момент запроса)

### Метрики диска:
- Мониторится **единственный накопитель** (корневая ФС VPS)
- **Формат вывода:** `Занято: <abs> | <percent>%, Свободно: <abs> | <percent>%, Всего: <total>`

### Uptime и перезагрузка:
- **Uptime:** `<Days> days, <Hours>:<Minutes>:<Seconds>`
- **Rebooted:** `DD.MM.YYYY, HH:MM (UTC+3)`

### Топ процессов:
- **Топ-5 процессов по RAM:**  
  Формат: `<№>. <название процесса> — <abs (MB/GB)> | <percent>%`
- **Топ-5 процессов по CPU:**  
  Формат: `<№>. <название процесса> — <percent>%`

**Метод сбора метрик:** на усмотрение разработчика (psutil, /proc, docker stats) — критерий выбора: минимизация ошибок и стабильность работы.

## 3. Мониторинг бэкапов `/backups`

### Поиск и парсинг:
- Путь: `BACKUP_PATH` из конфигурации (через pydantic-settings)
- Формат имени файла: `<db_name>_db_YYYYMMDD_HHMMSS.dump`
- Regex для извлечения `db_name` и `datetime`
- Отслеживаемые БД: **webui_db** и **litellm_db** (жестко заданные префиксы)

### Ротация и проверки:
- Для каждой БД хранится **не более 3 бэкапов** (последний / средний / ранний)
- После создания нового бэкапа выполняется **проверка синхронности**: если для одной из БД не найден бэкап с разницей по времени **не более 1 часа** от последнего бэкапа другой БД — отправляется **алерт о рассинхронизации**
- **Валидация размера:** если размер нового бэкапа отличается от предыдущего более чем на **15%** — отправляется **алерт о подозрительном изменении размера**
- Если бэкапов нет совсем — **создается новый бэкап** (триггер автоматического создания)

### Формат вывода:
```
Создан бэкап <db_name> (<datetime>)

Сохранены бэкапы:
webui_db:
  - Последний: DD.MM.YYYY HH:MM (<size>)
  - Средний: DD.MM.YYYY HH:MM (<size>)
  - Ранний: DD.MM.YYYY HH:MM (<size>)

litellm_db:
  - Последний: DD.MM.YYYY HH:MM (<size>)
  - Средний: DD.MM.YYYY HH:MM (<size>)
  - Ранний: DD.MM.YYYY HH:MM (<size>)

Общий размер: <total_size>
```

## 4. Мониторинг Docker-контейнеров `/docker_ps` и события

### Механизм мониторинга:
- **Docker Events API** с подпиской на события `start`, `die`, `stop`, `restart`, `oom`
- **Retry-политика:** при разрыве соединения — автоматический реконнект с экспоненциальным backoff (tenacity)
- **Батчинг при массовых событиях:** если несколько контейнеров падают в течение **1 минуты** — агрегировать события в **одно сообщение**
- **Троттлинг:** уведомления отправляются **не чаще 1 раза в минуту** для предотвращения спама

### Команда `/docker_ps` (сводка по запросу):
Формат вывода:
```
<название контейнера> — <статус (Up / Exited / Restarting)> | <uptime / downtime>
```

### События: Падение контейнера (`die`, `stop`):

**Классификация кода остановки:**
1. **Exit 0 (штатная остановка):**  
   Сообщение: `Контейнер <name> остановлен штатно.`

2. **OOM Kill (нехватка памяти):**  
   - Определяется по флагу `OOMKilled` в `docker inspect` и/или маркерам в системных логах (`/var/log/syslog`, `dmesg`)
   - Сообщение включает:
     - Пометку **[OOM]** в заголовке
     - Статистику памяти перед падением
     - Последние **20 строк** лога контейнера (tail)

3. **Exit ≠ 0 (ошибка контейнера):**  
   - Последние **20 строк** лога контейнера (tail)
   - Трейсбек выводится в **code block** (parse_mode=html: `<pre>...</pre>`)

**Обработка циклического рестарта (status `restarting`):**
- Собирается **только последний трейс** (не дублируется при каждой попытке рестарта)
- Отправляется **один раз**, повторные события игнорируются до изменения статуса

### События: Запуск контейнера (`start`, `create`):

- Сообщение об успешном старте: `Контейнер <name> запущен.`
- Последние **50 строк** лога (tail) для визуального контроля инициализации (warnings, info, debug-сообщения при старте)
- Логи выводятся в **code block**

### Real-time мониторинг логов:
- **НЕ используется** постоянная подписка на логи всех контейнеров
- Логи читаются **только при событии** (старт/остановка)
- Метод чтения: `docker logs <container> --tail <N>`

## 5. Healthcheck бота `/healthcheck`

- HTTP-эндпоинт (или Telegram-команда) для проверки работоспособности самого бота
- Ответ: `200. Статус: ок`
- Используется для мониторинга со стороны внешних систем (Docker healthcheck, uptime-мониторы)

# Архитектура и технические решения

### Хранилище состояния:
- **In-memory** (без персистентности)
- Архив событий/алертов **не ведется** (при перезапуске бота состояние сбрасывается)

### Graceful shutdown:
- При получении `SIGTERM` / `SIGINT`:
  1. Закрытие всех открытых соединений (Docker API, Telegram long polling)
  2. Flush логов
  3. Завершение работы

### Обработка ошибок:
- Если при сборе метрик или выполнении команды происходит ошибка (недоступность Docker daemon, таймаут, permission denied):
  - Отправляется **сообщение пользователю** с кратким описанием проблемы
  - Ошибка логируется (уровень `ERROR`)
- **БД для хранения ошибок не используется**

# UX и форматирование

### Parse mode:
- `parse_mode=html` для всех сообщений

### Интерактивность:
- **Inline-кнопки** (InlineKeyboardMarkup) для команд с выбором действий (если потребуется)
- Основные команды — текстовые (`/health`, `/backups`, `/docker_ps`)

### Единицы измерения:
- **Автоматический выбор:** KB / MB / GB в зависимости от величины
- 1 MB = 1024 KB, 1 GB = 1024 MB (бинарные префиксы)

### Форматирование текста:
- **Code blocks** (`<pre>...</pre>`) — для трейсбеков, логов контейнеров
- **Plain text** — для обычных уведомлений, метрик, статусов

### Формат дат:
- `DD.MM.YYYY` для даты
- `HH:MM` для времени
- Временная зона: **UTC+3** (конфигурируется через `TIMEZONE`)
